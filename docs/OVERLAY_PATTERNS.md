# Dialogs, alert dialogs and popovers

The complete compiling example is [13-overlay-patterns.ts](../examples/13-overlay-patterns.ts). It exports separate `overlayMarkup()` (HTML/styles only), `overlayOnLoad()` (self-contained frontend setup/bindings) and `submitOverlayAction()` (explicit backend transport). Construct no `FDO_SDK` instance during static composition. The release gate uses these exports from the installed package.

| Pattern                     | Required visibility and semantics                                                                                                  | Focus/close behavior                                                                                                                                             |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native `<dialog>`           | Closed markup omits `open` and `hidden`. Label with `aria-labelledby`. Call `showModal()` for modality.                            | Browser traps modal focus and fires `cancel` on Escape; `close` restores focus in the example. Cancel/Confirm call `close()`. `::backdrop` styles the top layer. |
| Custom `role="dialog"`      | Initially `hidden`, `aria-modal="true"`, `aria-labelledby`, `tabindex="-1"`. Opening clears `hidden` and makes background `inert`. | Example focuses Cancel, wraps Tab/Shift+Tab within its two buttons, closes on Escape/Cancel and restores the trigger.                                            |
| Custom `role="alertdialog"` | Same as custom dialog, plus `aria-describedby` for the short urgent description.                                                   | Example initially focuses the least destructive action, Cancel. Same modality and cleanup as the custom dialog.                                                  |
| Native `popover="auto"`     | No `hidden` attribute. Label content; example associates trigger with `aria-controls`. Call `showPopover()`/`hidePopover()`.       | Nonmodal; no focus trap. Example focuses Cancel, observes `toggle` for focus restoration after Escape/light dismissal and explicit close.                        |

Every example button has `type="button"`, so placement inside a form cannot accidentally submit. The native dialog's default Escape/cancel behavior is preserved; do not call `preventDefault()` on `cancel` unless you provide an intentional alternative. Both explicit Cancel and Escape restore the connected opener. If a rerender removes that opener, the host should choose a new logical focus target.

Visibility attributes matter: `hidden="false"` is still hidden in HTML; `open="false"` still opens a dialog. Use boolean props for these attributes. Custom `aria-modal` alone neither hides markup nor traps focus. Ensure `[hidden]` keeps `display:none` when applying custom display styles. An always-visible div with a dialog role is not a functioning modal. A popover is not a modal dialog, and native `dialog[open]`/`show()` is not `showModal()`.

The custom focus loop intentionally targets the two example buttons. For dynamic content, disabled/hidden controls, nested overlays, shadow DOM or arbitrary forms, implement a complete focus-management policy or use a native modal dialog. These extensions are not guaranteed by this example. Avoid multiple custom modals on the same background. The host must supply `inert`, native dialog and popover support in its Electron/browser version; no polyfill is bundled.

Cleanup closes open overlays, removes only the example's listeners, restores focus when it owns the focused overlay, and clears background inertness. Dispose `overlay-example` before replacing markup. Use distinct lifecycle keys and root-scoped selectors for independent views; namespace the fixed IDs if repeating this example.

The browser gate checks native cancel events via trusted Escape key input, accessible label references, modal initial focus, custom Tab wraps, Cancel, popover Escape, focus restoration, repeated initialization, rerender, backdrop CSS and teardown. It does not certify all assistive technologies or host iframe behavior. Host integration tests must verify focus across iframe boundaries and its sandbox/CSP.

These patterns follow the [HTML dialog specification](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-dialog-element), [HTML popover specification](https://html.spec.whatwg.org/multipage/popover.html) and [WAI-ARIA modal-dialog guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).
